  ---
  The SQLite Problem Kills Most Options

  Your store/ directory has 15+ SQLite databases in WAL mode. This single fact
  eliminates every network filesystem approach:

  ┌────────────────┬─────────┬──────────────────────────────────────────────┐
  │    Approach    │ Verdict │                     Why                      │
  ├────────────────┼─────────┼──────────────────────────────────────────────┤
  │ NFS (either    │         │ SQLite fcntl() locking unreliable over NFS.  │
  │ direction)     │ Dead    │ WAL mmap doesn't work. Documented corruption │
  │                │         │  risk.                                       │
  ├────────────────┼─────────┼──────────────────────────────────────────────┤
  │                │         │ Same locking issues. macFUSE kernel          │
  │ SSHFS/FUSE     │ Dead    │ extension increasingly hostile on Apple      │
  │                │         │ Silicon.                                     │
  ├────────────────┼─────────┼──────────────────────────────────────────────┤
  │ SMB            │ Dead    │ Worse performance than NFS, same locking     │
  │                │         │ problems.                                    │
  ├────────────────┼─────────┼──────────────────────────────────────────────┤
  │ Taildrive      │ Dead    │ WebDAV backend. Zero file locking semantics. │
  │                │         │  Alpha software.                             │
  └────────────────┴─────────┴──────────────────────────────────────────────┘

  Docker builds reading thousands of small files over any network mount would
  also be 3-10x slower. So even without the SQLite issue, mounts are the wrong
  tool.

  ---
  Two Approaches That Actually Work

  Option A: Claude Code SSH to Ryzen (Cleanest)

  Claude Code natively supports SSH sessions. You SSH into ryzen32 via
  Tailscale, Claude Code edits files that are already local to the Ryzen. Docker
   builds are local. kubectl is local. Zero sync. Zero latency. Zero corruption 
  risk.

  What you'd need: Node.js 18+ and Claude Code installed on ryzen32. Your
  .claude/ config already travels with the repo.

  What you'd lose: You'd be editing on the Ryzen's filesystem, not your Mac's.
  For deploy workflows, this is actually what you want.

  Option B: Mutagen One-Way Sync (Mac as Source of Truth)

  mutagen sync create \
    --name=halo \
    --sync-mode=one-way-safe \
    --ignore="store/" \
    --ignore=".git/" \
    --ignore="*.db" --ignore="*.db-shm" --ignore="*.db-wal" \
    ~/code/halo mrkai@ryzen32:~/code/halo

  Mutagen was literally built for this workflow. Docker acquired it. Sub-second
  propagation via FSEvents (Mac) and inotify (Linux). Files are local on both
  sides. SQLite databases excluded -- each machine keeps its own store/.

  Handles network drops gracefully. Queues changes, reconciles on reconnect.

  Bonus: Docker Buildx Remote Builder

  Skip file sync entirely for builds:

  docker context create ryzen --docker "host=ssh://mrkai@ryzen32"
  docker buildx build --builder ryzen-builder -t localhost:5000/halo:dev .

  Streams build context over SSH. No mounted filesystem. Practical for
  occasional builds but streams the entire repo every time.

  ---
  Recommendation

  Primary: Claude Code SSH for deploy workflows. The Tailscale mesh gives you
  1-5ms latency -- imperceptible for terminal interaction. This is the "one
  filesystem, no sync" solution you're describing, just achieved by moving the
  editor to where the files are rather than moving the files to where the editor
   is.

  Secondary: Mutagen for cases where you want to edit on Mac with near-instant 
  propagation. This gives you the best of both worlds at the cost of running a
  background daemon.

  3. The New Deploy Flow

  Before:  git add → git commit → git push → ssh ryzen32 → git pull → docker
